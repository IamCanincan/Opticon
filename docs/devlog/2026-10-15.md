- ✅ **【图标加载】落码：掩码按**内容**再认一次（`MonoCache` + `MonoKey`）→ 热重启 2 次现算 / 1880 次命中**
  （2026-10-15 04:21 构建 `6ad64c36…`，04:33:32 装机，两下重启验收：主人判「**图标没问题**」）。
  - **起因是他一句「现在每次重启桌面图标要加载好久，能不能优化一下」**，不是症状报告 —— 我先去的不是代码而是日志：
    装机前那一版（pid 7614）一次重启 **1594 次合成 / 只有 209 种内容**，同一张最多重压 **148 次**
    （高德 148 / 美团 142 / 抖音 138）。判"是不是同一张"不敢只看 8×8 指纹（它在 translate 那对上出过事），
    所以按 `edge + sig + fg 类 + intrinsic + adaptive` 逐字段对：**1593 行归成 216 个身份**，重复是真的。
  - **根因是一句写错的文档**：`MonochromeSynth` 里那个 `IdentityHashMap` 上面写着「图标对象由桌面的 IconCache
    长期持有、数量有界，所以这里不会无限增长」。桌面每次 bind 都 `getConstantState().newDrawable()`
    交**新实例**（`CircleIconDrawable.getMonochrome()` → `forIcon(sourceIcon)`），于是那层缓存结构上命中不了。
    ⚠ 教训：**文档里的前提也是待验的读数**。这条前提撑了一天多的"缓存已经有了"。
  - **键的六个输入**：`掩码 = f(像素, 层底像素, edge, adaptive, flatten, 强制裁圆)`，判据与几何都从这六样里推出来，
    所以不进键；`circleEnabled` 是唯一能在两次重启之间变的运行时输入，必须进。**全像素扫不抽样** ——
    抽样的漏检代价是交出**别的图标**的掩码，而离线量出来键只要 **0.15 ms**（模型 389 ms 的 0.038%），
    省这个钱毫无意义。64 位哈希在 209 个条目上撞一次约 1e-15，比内存里一个位翻转还低。
  - **两层怎么分工**：内存 8 MB **故意不追求装下整个抽屉**（209 种 ≈ 30 MB，那笔钱常驻在桌面进程里不划算）；
    于是内存被扫穿是**设计内**的，漏下去的落到磁盘（几毫秒）而不是落到模型（三百多毫秒）—— 正因为磁盘兜着，
    内存层才能用最便宜的"弹出最旧那一张"，不用算加权。磁盘 48 MB 按 `lastModified` 淘汰，
    落在**宿主**的 `cacheDir`：我们就跑在那个进程里，用自己的 Context 写自己的目录；
    换到模块自己的 dataDir 是跨 UID 写，权限拒绝。**没有第三种选择。**
  - **目录名认 `lastUpdateTime` 不认 versionName**（与桌面图标缓存戳记 `renderId()` 同一个函数、同一条理由，
    顺手把那个 `private` 改成 `internal` 让两处共用）：算法每装一次就变，版本号只在正式发版时动。
    这条要是写错，接下来几轮迭代会看见**上一版画的那张** —— 而它在日志上完全合法。
    拿不到装机身份就**整层磁盘关掉**：宁可不快，不给旧答案。
  - **负缓存**：`判据不成立、放弃合成` 那几张也记（只记内存）。它们同样被重压 148 次，
    一次模型都省不掉就是纯浪费；降级出口与原来逐字一致（返回 null，桌面走它自己的 Factory），所以行为没变、
    只是不再重算。
  - **`rowBytes` 存当时那个真值、读的人再核一遍** —— 而不是两边各按 `edge` 算。ALPHA_8 补不补到 4 的倍数
    在不同实现上不一样（本仓已经在 ASCII 缩略图那里踩过一次「按 `w` 读、每行挪 `(stride-w)`，看着像掩码碎了」），
    两处一旦不同就是**永远不命中**，而那种失败在日志里只长得像"这台桌面不缓存"。
    ⚠ 真机这一趟磁盘读了 **480 次、零条「解不开 / 对不上 / 写不进去」** —— 这条假设被装机验证了。
    写入走 `*.tmp` + `rename`（同目录原子）：桌面进程随时会被杀，半个文件比没有文件糟得多。
- ⚠⚠ **本日最大的量具事故：我自己的负例是假的**（新增第 15 闸 `MonoKeyKt.kt`，1972 条）。
  行步长那条负例写成 `decode(enc, e, e)`，而 96/192/384 三档上 `e == (e+3)/4*4` —— **根本没构造出坏的输入**，
  解开来完全合法，却报「通过」。第一跑就是这三条红（`坏-行步长不符 @96/@192/@384`）把它暴露了。
  修法：给一个**不等于存进去的那个**值（`stride + 4`），再加一条 `rowBytes = 0`。
  同一段还顺手改了**成本的单位**：键 0.15 ms 在毫秒口径下报 **0 ms**，看起来像"快得看不见"，实际是被 JIT 抬走的风险 ——
  换成 ns 计、断言「两趟都 >0」。**负例必须是真坏的，否则它只是在替我的假设背书。**

- ❌ **【已否决，读数为据】「把实例层的键换成 `ConstantState`，在取像素之前就命中」这一刀不做。**
  它要省的是每次命中仍付的那一笔光栅化 + 哈希（哈希离线量 0.15 ms，光栅化是桌面的活儿）。
  先只加读数、不加优化（提交 `6b2c8bf`）：`describe()` 末尾打 `state=<ConstantState 的 identityHashCode>`，
  判据行与命中行都打 `键=<hex>`，且与磁盘文件名共用同一个 `MonoKey.hex`（拿着日志能直接数目录）。
  装完按一次重启，`_harness/_statekey.cjs` 数出来：**1043 次请求 → 1043 个不同的 state、225 个不同的内容键**，
  **按 state 命中能省掉的重复 = 0**。分类看也是同一结论：`AdaptiveIconDrawable` 607 次对 602 个 state、
  另一类 448 次对 441 个 —— 桌面**每次 bind 连 state 都是新造的**。
  两种解释（它真的每次新建 state / 那个 getter 每次都返回新对象）**指向同一个决定**：按 state 建一层缓存永远命中不了。
  否决票那一面也顺手看了：**0 个 state 对出两个内容键** —— 所以不是"共享了但不敢用"，是**根本没有共享**。
  ⚠ 这一条不是"我没量到"，是量到了零。换一台桌面若要重开，先把 `_statekey.cjs` 跑一遍看共享率再说。

## 复查轮（主人：「功能有些许更改，看看有没有说明之类的要改，顺便再检查一遍代码」）

- ✅ **代码复查叫了一份独立视野**（同一个上下文里读自己写的东西会一路点头）。它交了九条，六条我认、三条我拒，逐条对着代码核过才动手：
  - **负缓存命中一行日志都不打** —— 我写的是 `if (hit.mask != null) noteCached(...)`。后果不是"少一行"，是
    **`放弃合成` 这条 telemetry 从每 bind 一次塌成每内容一次**（真机 148→1），日志上读起来像"这台桌面根本不放弃合成"。
    本仓第四次吃同一类"提前 return 静默"的亏 —— 而且这次是我自己刚立完规矩的下一分钟。**改**：两种命中都打，负的那种写 `判据不成立（负缓存，未重算）`。
  - **命中会吃光冷启动那 12 条重诊断名额**（全画布直方图 + 连通块 + 缩略图）。热重启 1880 次命中几秒内把名额耗干，
    **真正现算的那两张反而一张缩略图都没有** —— 而现算那两张才是要核对的东西。**改**：两条路各一套名额（12 / 8）。
  - **`dirTries` 会被 attach 阶段的正常窗口烧光**：`renderId()` 内部第一步就是 `currentApplication()`，那会儿它常常是 null
    （这条坑 IconHooks 里早就写着），于是"没就绪"被当成"确定失败"计数，头三次 bind 一眨眼用完额度 → 整层磁盘**永久**关掉。
    **改**：顺序换成**先 Context 后要身份**，只有"拿到 Context 却建不出目录 / 拿不到身份"才计数。
  - **`cacheDir` 被系统清掉之后 `dir` 被钉死**：之后每个图标写都抛 → 每个图标一行警告，且这一层再也不会回来。
    **改**：写失败就把 `dir` 忘掉（下一张重新解析），警告只放行前 3 条。顺带 `app.cacheDir` 这句本来在 `runCatching` 外面。
  - **`note()` 只在磁盘那一支调** → "全内存命中"的一趟重启（真机第二下正是 1400/1880 在内存）**一行汇总都不出**。改成两支都打。
  - **OTA 不动我们的 `lastUpdateTime`**，而 `ALPHA_8` 的 `rowBytes` / ColorSpace 这类"像素没变、交付口径变了"的东西只有系统侧会动，
    内容键盖不住 → 目录名补 `_api<SDK_INT>`。**这条是加固，不是修 bug**：真机上没有观察到这种错。
- ❌ **拒掉的三条，理由写在这里**（免得下一轮又被自己说服）：
  · 「把 `pruneOldBuilds` / `sweep` 挪出锁」—— 它们分别是每进程一次与每 64 次写一次，量级是几毫秒；为了这个把两层缓存的
    时序拆开，换来的收益看不见，风险是新的。**并行化那一刀刚被读数否掉，同一晚上不该再叠第二刀未量的重构。**
  · 「两层各 8 MB 要合成一个预算」—— 两层的位图是**同一批对象**，合并记账会让实例层失去自己的上限（它现在靠这个上限清掉引用）。
    改为**在文档里把"这两个 8 MB 不是两道独立的墙，是一道半"写清楚**（最坏常驻 16 MB）。
  · 「`state=` 那一位是假尺，删掉」—— 半对：`CircleIconDrawable.getConstantState()` **每次调用新建一个匿名 ConstantState**
    （那个 override 是我写的），所以走包装的路径上它永远"独一无二"。**但今天那批读数里一张 wrapper 都没有**
    （`AdaptiveIconDrawable` 607 / `BitmapDrawable` 405 / `VectorDrawable` 32 / `LayerDrawable` 10 / `GradientDrawable` 1），
    所以那条否决站得住。**不删，改成自己标出来**：wrapper 打 `state=-wrap`，读到 `-wrap` 就知道这一位在这个类上没定义。
- ⚠ **复查顺手纠正的那句错文档**（这才是最值钱的一条）：`IdentityHashMap` 上面那句「图标对象由桌面的 IconCache
  长期持有、数量有界」——**它是整层缓存设计的前提，而它是错的**。装机数：1594 次合成 / 209 种内容、这一层命中 ≈ 0。
  文档里一句没被量过的前提，能让一层缓存错一整天。现在那句话改成了"这一层已经退化，真正干活的是 `MonoCache`"。
- **给缓存的前提补了闸**：十四道旧闸量形状，**没有一条量"同一批输入两次算出同一张"** —— 而缓存说的恰恰是后者。
  第 15 闸加两条：同线程**夹一张别的图**再跑要逐字节相同（查上一张残留）、**换一条线程**跑同一张要逐字节相同
  （`MonochromeMask` 用 ThreadLocal 复用暂存，起点不同就是两次答案不同）。**这是整个功能唯一没被任何旧闸覆盖的前提**。
