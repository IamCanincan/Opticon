- **宽幅式 / 五角星式的图标，块头永远比实心的小一档**（2026-10-14 定，**不再试**）：
  "不规则"那一类（按圆裁下去只剩 <60% 图案）走"不裁 + 缩进圆里 + 圆内补白底"。其中
  **外缘先顶到圆边**的形状（一条宽横幅、一个五角星、一个空心环）——想让它们和实心的一样"块头"，
  唯一办法就是把外缘裁掉一块（B 案）。**这条被主人否掉**："图案就是得完整的，不能光看占比。"
  于是墨量对齐只能**往小里对齐**（窗口取三条约束的最大值，见 `IconCropWindow` ③），永远不许切外缘；
  那几种的墨量因此停在 20~23%（实心 50%），是**几何决定**，不是门槛没调好。
  数字与对照：离线合成形状那张表列了四个走"不裁"的 —— 20%(横幅)/22%(三角)/23%(星形)/50%(环)，
  **可复现**：那 5 个形状是 `_circab.cjs` 内部生成的，`node _circab.cjs <语料png>` 就跑得出来（2026-10-14 重跑逐字对上）。
  ⚠ 但 `PLATE_INK` 注释里那组 18% / 29% / 38% **本轮没复现** —— 它不是同一次量测，两处数字别混用、也别互相"对齐"。
  B 案的对照图在 `_harness/_ab2.png` 第 4 格。⚠ 别再把"允许裁外缘"提回来 —— 那是同一条路。
  屏上实测过两轮：预测图案占白圆 **70% → 实测 70.6%**（主人判"这个尺寸差不多"）—— 这一条两侧同为
  直径分数，成立。⚠ **作废一条**：更早那句"设计外缘 0.903 → 屏上 0.906、模型与真机对上了"**是单位串了**
  （2026-10-14 发版前复核）。0.903 是 `TIP_FLOOR/SHRINK_EXTRA` 的**半径分数**，而 0.906 是
  `1 − 余量%`，那个"余量 9.4%"按 `_discmeasure.cjs:63` 的算式其实是**直径分数**（真半径分数是它的两倍），
  两边不是同一个量。同一张铃铛按半径分数正经量出来是 **0.811**，与当时的设计值 0.903 差 9 个点，
  而且那张量具的 inset 把窗口截在 0.9·R —— **它根本量不到 0.903**。这条只当"没量到"，别再引用成模型验证。

  下面这段就是这份模型（`circle/MonochromeMask.kt`）的说明 —— **它现在就在屏幕上**，
  判据台与真机重放跑的也是同一份：

  模型只问一句「**这个像素与它*周围*那块参照差多少**」，一个量 `dep = a×[(1−β)+β·ΔE/100]`
  应用两遍（参照 = 背后的底 / 近旁的主体）：
  1. **底 = 内容框四个角上的那几族颜色，铺成一张局部色场。** 每个角往里找一个落在底上的窗口
     （圆角/圆形图标角点是空的，所以沿对角往里走），得到 ≤4 个颜色家族；洪泛一次穿过**所有**
     家族 —— 底是它们的并集。⚠ 不是"哪个候选摘掉的面积多就选哪个"：真机的底常常是**几块拼的**
     （高德四块、云闪付红白两段、饿了么橙蓝两段），只选一个家族，剩下那块底整块变成墨。
     然后把每格的底色**传播**到整张画布：一个像素的参照色 = 离它最近的那块底，不是"它落在
     哪个格子里" —— 按格子取会让字形在格界上跳一级浓度，也会把两块底之间的抗锯齿混色算成墨。
     中缝另有一条按位置的吸收（两侧底色差得开、且这块够细才吞）。
     「拟合场 → 重算距离 → 重新洪泛 → 吸收中缝」跑 3 轮，容差每轮由底板自己的散度定
     （下限 `TOL_MIN` 兜着：网格一细，散度会被量成 0，洪泛随之只容得下逐像素同色，渐变尾端
     整个留在掩码里 —— 这是所有局部背景模型的通病）。渐变底在每个格子里都有自己那一份，
     所以**渐变不需要并层、不需要档内插值补偿**。
  2. **差 = CIELAB ΔE76**，整数查表，再按像素自己的 alpha 收一道覆盖率。不用 RGB 曼哈顿距离，
     也不只用亮度。
  3. **alpha = 两点标定 + 一条单调曲线**。零点 = 底板自己的散度（这张图量出来的，不是绝对值），
     实心点 = 形层距离的 66 分位，中间过 `t^0.75`。于是「一整块色板」不是被闸门拦掉的，
     是**产生不出来** —— 底板与自己比必然差 0。
  只剩一支例外：**透明底**。底是「没有东西」时色场没有可比对象，差退成覆盖率 = 图标自带的
  alpha（原样保留、不做形态学）；但会再补一步**内部镂空**：参照物换成图形自己的主色，
  只把**被主体围住**、又与局部主色差得多的那部分按差多少镂空（贴着背景的那一半是图形的
  另一部分，不算镂空）。
  ⚠ 这条链与通知小图标**不再是同一份实现**：通知交出去的是完整位图、且先 `fill` 把内容
  放大填满画布；桌面只有一条 alpha、且必须对齐 108dp 画布。以前共用四个入口，共用逼着
  每条判据对两边都成立，结果两边都不准 —— 现在两边只剩 `rasterize` / `foregroundOf`
  这种没有判据的事是共用的。
  还有**最后一级**：这张图根本没有"底"可摘（整张插画、照片底 —— 四族底也只摘得掉一小块）
  时，不退回桌面，而是把**它自己的明暗层次**搬到 alpha 上（越暗越实，端点按这张图的
  p5/p95 量）。只有光栅化失败、或整张连 12 个 L\* 都没散开（一张纯色，确实没有层次可搬）
  才返回 null。
  ⚠ 但**回落不是中性的**：桌面那条 Factory 算的就是错极性，所以放弃率上升是回归信号。
  这条链关掉总开关就整个停（界面上那条），平时它自己不动遮罩的判据也只在日志里看（`Mono: diag#N … 放弃合成：…`）。

- **掩码缓存命中之后，每次仍要付一次光栅化（模型已经全省掉）—— 上游那条路已量死，不再试**（2026-10-15）。
  `MonoCache` 的键是**内容**键，而拿内容就得先把图标画出来：`getMonochrome()` → 光栅化 384² → 取像素 →

  前 300 张上屏 **63.5 s → 5.07 s**，剩下的那一点是"每次都把图标重画一遍"。

  而且**必须让内容键兜底**（state 相同而像素不同 = 交出别的图标的掩码，那是错，不是慢）。

- **Lawndesk 那条「10% 透明口径」不能搬：同名不同义，搬过来方向是反的**（2026-10-15 读该仓时核到，**已量**）。
  他们的「满幅」= 墨铺满**自己的外框** ≥90%（`lawnchair/.../AdaptiveIconGenerator.java:181`），而**用途是**

- **应用声明了两份图标时，两份各归各的：`icon` 归我们、`roundIcon` 留给平台**（2026-10-15 主人裁决，已装机验收）。
  桌面给**圆形遮罩**环境优先取 `roundIcon` 那份，应用信息页（Settings）走 `icon` —— 所以同一个应用两屏
  **天然不同源**，不是缺陷。真机案例 `com.github.standardadb`：`icon` = `res/drawable/ic_launcher.png`
  （512² 白底位图、无透明通道），`roundIcon` = `mipmap/ic_launcher_round.xml`（`anydpi-v26` 那份自适应，
  前景是矢量 `drawable/ic_launcher_round_foreground.xml`）—— **两张不是同一幅画**。
  ⚠ **本轮唯一一次翻案，记在显眼处**：我一度把 `ApplicationInfo.roundIconRes` 也打上标记（"两边都归我们管"），
  装机后主人一眼判掉：「**原桌面图标就是一个完美的圆了**」。他是对的 —— 桌面那份本来就是自适应图标、
  平台画得就对，标记它等于**把对的抢进我们的内切圆流程**。**已撤回**（`markIconResId` 只标记 `icon`），
  并在"未标记"那条口子上补了 `passed is AdaptiveIconDrawable → 不碰`，免得按资源名那两条判据再误伤它。
  ⚠ 字段名也是这一轮才认准的：桌面 dex 读的是 **`ApplicationInfo.roundIconRes`**；`roundIcon` 在 framework 里
  只是 `android.R$attr` 的常数 —— 我第一次改的那个名字**压根没生效**，而且它不报任何错。
  **How to apply:** 再遇到「桌面和应用信息页不一样」的报法，**先查这个应用声明了几份图标**
  （`aapt2 dump resources <apk> | grep -i ic_launcher`）：两份不同资源 → 天然不同源，回这一条；
  只有一份 → 那是**缩放**差异（同一幅画被平台缩了），属我们该修的（`Hook.JiuWu.Xp` 那类）。
  ⚠ 已知残留：只声明 `roundIcon`（没有 `icon`）的应用，`unmarkedAppIcon` 那一支只比 `app.icon`，这一版会漏。

- **图标标记 id 不再假设应用资源住在 `0x7f`**（2026-10-15 换掉"顶字节换 `0x6e`、还原时 OR 回 `0x7f`"那套）。
  真机 `Hook.JiuWu.Xp` 的 APK **5701 个资源全在 `0x95` 包号下**（`aapt2 link --package-id 0x95`）——
  老写法同时坏两处：还原回去的 id **指向错的包**（加载要么抛、要么解成别人的资源），
  而打标记那道闸（`isAppResource`）原来**也只认 `0x7f`**，于是这类应用**从头到尾没被打过标记**、
  裁圆那条路永远碰不到它（桌面与应用信息页因此不一致）。现在标记 id 的低 24 位是**槽位号**，
  真身存在进程内两张表里（`markSlots` 原 id→槽位 / `slotOrigin` 槽位→原 id），应用的包号是多少都不影响。
  同一处还把"参数里哪个 Int 是资源 id"的判据从 `v > 0x1000000` 换成 `(v ushr 24) != 0`（`resIdArg`）：
  包号 ≥ `0x80` 的 id（`0x950f0009`）在**有符号** Int 里是负数，老比较会把它们整批滤掉。
  **有意留的边界**：槽位表是**进程内**的 —— 打标记与还原必须发生在同一进程
  （加载出口，或跨 Binder 前 `writeToParcel` 那次反标记），跨进程不共享；
  上限 `MARK_SLOT_LIMIT = 4096`，超了整表重来，那之后**旧标记 id 解不回去**
  （`unmarked()` 退回 `0x7f` 老写法 → 非 `0x7f` 包号的解不出）。图标 id 每进程是几百个量级，够用。
  **How to apply:** 再看到「某应用桌面与应用信息页不一致、而我们的判据行里一条都没有」，
  先查它的资源包号（`aapt2 dump resources <apk> | head`）—— `0x7f` 之外的老写法会整批隐形。
